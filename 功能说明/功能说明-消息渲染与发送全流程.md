# 功能说明-消息渲染与发送全流程

## 1. 消息渲染流程 (异步高性能架构)

系统采用了先进的 **Web Worker + 异步渲染管线** 架构，将计算密集型的 Markdown 解析和代码高亮任务移至后台线程，确保主线程 UI 响应的丝般顺滑。

### 1.1 渲染管线概览 (Pipeline Overview)

渲染核心函数 `formatMessagePipeline` 已升级为全异步 (`async/await`) 模式，其流程如下：

1.  **后台预处理 (Web Worker)**:
    -   **正则预处理 (Stage 1)**: 在 Worker 中执行所有的 Pre-Markdown 正则替换，无需占用主线程。
    -   **Markdown 解析 (Marked)**: 使用 `marked.js` 将 Markdown 文本转换为原始 HTML。
    -   **代码高亮 (Highlight.js)**: 对代码块进行语法高亮处理。
    -   **代码块增强 (Enhancement)**: 生成代码块的 Header、复制/下载按钮等 HTML 结构（纯字符串操作）。

2.  **主线程后处理 (Main Thread)**:
    -   **安全消毒 (Sanitization)**: 接收 Worker 返回的 HTML，立即使用 `DOMPurify` 进行 XSS 过滤（因为 DOMPurify 依赖 DOM API，必须在主线程运行）。
    -   **正则后处理 (Stage 2)**: 执行 Post-Markdown 正则替换（涉及 DOM 操作的部分）。
    -   **样式修饰**: 执行 `applyColorFormatting` 等轻量级 DOM 修饰。
    -   **JSON 表格增强**: 将 JSON 代码块转换为可视化的表格组件。

### 1.2 竞态条件防御 (Race Condition Prevention)

由于渲染变为异步，系统引入了 **`currentRenderId` 锁机制** 来防止多重渲染导致的 DOM 混乱：
- 每次调用 `renderChatMessages` 都会生成一个新的 `renderId`。
- 在异步操作（如 `await displayMessage`）的每一步之后，都会检查当前 `renderId` 是否仍是最新的。
- 如果发现 ID 不匹配（说明有新的渲染任务插队），当前任务会立即中止，防止将过时的 DOM 节点添加到页面上。

### 1.3 智能增量更新 (Incremental Updates)

在流式输出过程中，系统使用 `updateDomPreservingCodeBlocks` 机制：
- **原地更新**: 通过 `data-block-id` 识别并复用代码块 DOM 节点。
- **状态保留**: 仅更新代码内容，保留 Header 和按钮实例，确保用户在生成过程中点击按钮的操作不会被打断。
- **侧边栏联动**: 在 DOM 更新时触发 `tryAutoExpand`，尝试同步代码预览侧边栏。

## 2. 消息发送流程

### 2.1 触发与准备
- 用户点击发送 -> 调用 `handleSendMessage`。
- **关键改进**: 在开始流式请求前，**`await renderChatMessages`** 确保空的 AI 消息气泡已完全渲染并挂载到 DOM 中。这是后续流式更新能找到目标元素的前提。

### 2.2 请求构建 (`buildApiRequest`)
- 统一负责组装 System Prompt、Persona、WorldBook 和 History。
- 根据 `mcpSettings.enabled` 决定是否注入工具描述。

### 2.3 流式响应处理 (`handleStream`)
- **状态管理**: 设置 `state.streamingConversationId`。
- **节流渲染**: 使用 `throttledRender` (100ms) 控制 DOM 更新频率。
- **多轮工具调用 (MCP Multi-Round)**:
    - 如果工具调用触发了 `process_result`，`handleStream` 会调用 `continueConversation`。
    - **v4.0升级**: `continueConversation` 支持最多10轮循环工具调用，每轮创建独立 DOM 容器，详见 `mcp请求到渲染全流程.md`。
    - **状态保护**: `continueConversation` 会设置 `state.isFollowUpStreamActive` 标志，并为每轮请求创建**新的 `AbortController`**。
    - **停止按钮**: 通过检测 `hasTriggeredFollowUp` 状态，确保在分析阶段，"停止"按钮依然有效且能正确中止新的请求。

### 2.4 模拟发送与提示词透视 (`simulate-send-modal.js`)
- **顶栏交互重塑**:
    - 将会话数据详情入口与 `#session-token-badge` 合二为一，升级为复合胶囊按钮，保留点击查看正文/思考/隐藏明细功能；
    - 原位置重构为【模拟发送】按钮（`#simulate-send-btn`），用于发送前全面透视。
- **全链路前端模拟与严格净化**:
    - 在绝不发起任何后端网络请求的前提下，自动提取输入框草稿或当前上下文；
    - 严格前置执行 `processAndFilterMessages` 净化流水线：**剔除所有被标记隐藏的楼层**、注入长期记忆总结、追加 MCP 工具结果、严格应用 `messageLimit` 最近消息限制；
    - 彻底剥离 `rawContentWithTools`、`thinking`、`isDraft` 等内部中间字段，输出 100% 真实纯净的 `{ role, content }` 请求载荷；
    - 若配置了消息数量限制，在弹窗顶部仪表盘展示**红字醒目提醒**（如 `⚠️ 已限制发送最近 6 条可见消息`）。
- **三维透视视图与交互增强**:
    - **📑 结构流卡片**: 逐条展示发出的消息来源（人设/记忆/备忘录/草稿）、独立 Token 与字符数，支持**一键全部展开/全部折叠**、单条折叠与独立复制；
    - **📝 平铺纯文本**: 展现实体上下文全文字符流；
    - **💻 请求 JSON 载荷**: 选项卡采用平角下划线指示器，输出符合 OpenAI / Claude 标准接口格式的完整纯净 JSON，支持一键快速复制。

## 3. MCP 工具调用流程

### 3.1 独立处理模块 (`mcp-handler.js`)
- 负责解析、执行和结果渲染。
- 新增返回值 `{ content, hasTriggeredFollowUp }`，供主流程判断是否需要保持流式状态。

### 3.2 侧边栏策略
- `CodePreviewManager` 会自动拦截 `language-tool_call` 类型的代码块，防止 MCP 工具调用的 JSON 数据误触发侧边栏展开。

## 4. 错误处理与调试

- **数据类型防御**: `markdown-engine.js` 增加了对非字符串输入的防御逻辑，防止因历史脏数据导致的页面崩溃。
- **调试模式**: 完整的请求/响应日志会通过 `createDebugResponseLog` 发送到调试端点。
